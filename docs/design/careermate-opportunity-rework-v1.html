机会页：从「取数修复」到「真实推荐产品」

0背景

前情 · 已上线 跨组织取数已修复：机会列表原本恒为「暂无机会」，根因是 JD 库（KB 599，职场数据分享 org316）被产品组织的 API-Key 跨组织访问、RAGForge 静默返回空。已按知识库路由双 Key（RAGFORGE_DATA_API_KEY）并上线，生产实测深圳岗位正常返回。本方案在此基础上继续。

当前机会页暴露出四个待办：

#问题现状 / 根因
1条数被卡在 ~29列表总数=检索 topK 去重后的 JD 数。searchTopKFor 首页取 topK=30，经 ChunksToOpportunityConverter 按 docId 去重 ≈ 29 条；topK 还随页码涨、上限 100，导致 total 跨页不稳定。
2冷启动无展示逻辑新用户无简历、无画像时如何推荐？现仅有一套写死 广州 / Java 后端 的兜底，不理想。
3代码含 demo 口径这是真实产品，代码与设计不应出现 demo / 演示 字眼。现存 MODE_DEMO / demoMode / asDemoItem 等一批命名待清理。
4分页样式不统一无公共分页组件，机会页自写 .pager，资产库 / 对话 各不相同。

1目标与非目标

目标

  • 有画像 → 精准匹配；无画像 → 真实通用推荐。全程真数据、无假匹配。
  • 条数放开到合理匹配池，total 跨页稳定。
  • 筛选驱动：默认城市 + 动态城市下拉。
  • 去除全部 demo / 演示 口径，产品化命名。
  • 全站分页组件统一为标准样式。

非目标

  • 不做全量分页（撤 Option 2）——见决策 D1。
  • 不改 RAGForge：不新增/开放 RAGForge 端点，改动收敛在 CareerMate 前后端。
  • 不把机会页变成「可刷完整个职位库」的职位板。

2关键决策

D1 · 不做全量分页，走「默认过滤 + 匹配池扩大」 机会页是按画像匹配的推荐流，用户只看最相关的前几十个；价值在匹配与排序。全量分页（按时间刷上千条）会把差异化稀释成职位板，且需跨仓库改 RAGForge 白名单、每页额外打分、城市只能按文件名近似过滤——低用户价值 × 高实现成本。故撤销全量分页。
决策结论影响面
D1不做全量分页；匹配池扩大到合理上限、total 稳定，池内分页。后端
D2冷启动三档：有简历 / 有意向无简历 / 纯新用户，逐级降级到「通用推荐」。前后端
D3清理全部 demo 命名与文案，改产品化措辞（逻辑不删，仅改名与口径）。前后端
D4抽公共分页组件，统一为「第 X–Y 条 / 共 N 条 · 每页选择器 · ‹ 页码 ›」。前端

3方案详述

3.1　匹配池扩大 & total 稳定（后端）

  • 把检索取数与页码解耦：列表固定按匹配池上限取 topK（建议 150），去重后作为稳定 total，分页仅对内存池切片。
  • 调整 OpportunityServiceImpl.searchTopKFor 与 MAX_SEARCH_TOP_K；total 不再随页码变化。
  • 匹配池是「最相关的前 N 个」，非全库——与推荐定位一致。

3.2　默认城市 + 动态城市下拉

  • 进页默认城市 = 画像目标城市（targetCity）；无则由定位/轻问答得到（见 3.3）。
  • 城市下拉从写死的 10 个改为「有岗位的真实城市集」。来源见开放问题 Q1，推荐离线/定时聚合：定时任务对 JD 库算「城市→岗位数」索引存 CareerMate 侧，下拉只显示有岗位的城市、按数量排序、周期刷新。运行时零 RAGForge 依赖、零 per-request 成本；上线前可用「全国主要城市表」兜底、聚合就绪后无缝替换。（注意：运行时 API-Key 打不到 RAGForge 文档列表端点，故不走运行时实时聚合。）
  • 城市对结果的作用：现为拼进语义 query（非精确过滤）。本期保持语义参与即可，精确过滤列入后续增强。

3.3　冷启动三档（去 demo 化）

档 1
有简历 → 个性化匹配态：命中 / 缺技能徽章 + 匹配度排序（现状保留）。
档 2
无简历、有意向（targetRole / targetCity，来自注册或 agent 对话自动抽取）→ 通用推荐态：按意向岗位+城市出最新机会，不展示匹配徽章（无技能不摆假分），徽章位换成薪资/最新标签 + 「上传简历解锁匹配」CTA。
档 3
纯新用户（无任何信号）→ 进页轻问一句（岗位+城市）或用定位，出对应城市的「最新机会」通用流 + 强引导上传简历。（问答 vs 定位见开放问题 Q2）
原则 绝不给无画像用户展示假匹配分；冷启动的「最新浏览」是降级态而非核心态；有上限、按默认城市，不是无限翻页。

3.5　全站分页组件统一

抽一个公共分页组件，样式对齐目标：第 X–Y 条 / 共 N 条 · 每页 [10 ▾] 条 · ‹ 1 ›。

  • 能力：总数展示、当前区间、每页条数选择、上一页/下一页、页码。
  • 应用范围：机会页（替换自写 .pager）、资产库、对话历史等现有分页/滚动处。
  • 桌面用完整分页；移动端沿用滚动加载但复用同一数据契约。

6开放问题（需你拍板）

Q问题选项 / 建议
Q1城市下拉来源建议：离线/定时聚合 JD 库的「城市→岗位数」，存 CareerMate 侧，下拉只显示有岗位的城市、按量排序、周期刷新（运行时零 RAGForge 依赖）。推荐　备选：① 后端全国主要城市表（简单但可能含空城市、非真实分布，可作兜底）；② RAGForge 加 distinct-city 端点走实时（需改 RAGForge，且运行时 API-Key 现打不到文档列表）。
Q2纯新用户冷启动方式进页轻问答（岗位+城市，相关性最高，建议）　/　定位默认（无打扰但较粗）。
Q3匹配池上限具体值建议 150；可 100 / 200。越大越慢且低相关噪声增多。
Q4每页默认条数建议默认 10，可选 10 / 20 / 50。
Q5冷启动「岗位」输入形态建议：输入框 + 联想（combobox），自由文本覆盖全部岗位，联想复用现有「岗位联想」。推荐　不建议封闭下拉（岗位为开放词汇，无法枚举全部）。城市仍用下拉。

7风险

R1 · 接口契约 VO demo 字段改名须前后端原子同步，否则线上字段错位。建议同一 PR 内前后端一起改。
R2 · 匹配池上限的取舍 上限过高会拖慢检索并引入低相关结果；过低则小众城市结果偏少。需结合筛选一起调。
R3 · 城市语义 vs 精确 城市当前仅参与语义 query，非精确过滤；「城市·深圳」可能混入近似结果。精确过滤列入后续增强，本期不阻塞。
