PART 01项目定位

CareerMate 是面向求职者的 AI Agent 应用层，通过工具调用、记忆管理和 RAGForge 知识检索能力，完成简历分析、岗位匹配、面试训练和求职进度管理等多项任务。知识检索通过 RAGForge REST API 获取，CareerMate 不重复实现底层检索能力。

  • 不是 RAG 管理后台 — 不负责文档导入、解析、切分、Embedding、向量索引等底层处理
  • 不是普通聊天壳子 — 有独立的 Agent 引擎、分层工具系统、记忆管理和求职业务流程
  • 是求职任务工作流 — Agent 自主规划多步骤任务，调用工具链完成简历分析、岗位匹配、面试训练

一句话定位

2.4 简历与 RAGForge 知识库隔离

用户私有简历默认不进入共享 RAGForge 知识库。CareerMate 自行完成简历文本提取（Apache Tika）和结构化画像生成，简历原文仅存储在 CareerMate 的 PostgreSQL 中。如需将用户简历纳入 RAGForge 检索范围，CareerMate 记录 user_id → ragforge_kb_id 映射，为每个用户创建独立 RAGForge 知识库，实现架构层面数据隔离。

2.5 RAGForge 调用方式

CareerMate 通过 RagForgeClient 以服务级 API Key 调用 RAGForge。用户权限完全由 CareerMate 的 Spring Security + JWT 控制，RAGForge 不感知终端用户身份。

PART 04LLM 供应商抽象

系统不绑定特定模型供应商。核心架构通过 LlmClient 接口隔离模型实现，方便开源用户替换模型，测试环境可使用 Mock 实现。

4.1 LlmClient 接口 (SseEmitter + StreamCallback)

后端基于 Spring MVC（非 WebFlux），SSE 流式响应采用 SseEmitter + StreamCallback 模式：

public interface LlmClient { ChatResponse chat(ChatRequest request); void streamChat(ChatRequest request, StreamCallback callback); // StreamCallback: onToken(String), onComplete(ChatResponse), onError(Throwable) ToolCallResponse toolCall(ToolCallRequest request); } // Controller @PostMapping("/api/agent/sessions/{id}/messages/stream") public SseEmitter sendMessage(@PathVariable Long id, @RequestBody MessageRequest req) { SseEmitter emitter = new SseEmitter(300_000L); agentRuntime.execute(id, req.getMessage(), new SseEmitterCallback(emitter)); return emitter; }

4.2 SSE 连接生命周期管理

管理项实现方式
独立异步线程池Agent SSE 执行使用独立线程池 agent-executor（核心 4 / 最大 20 / 有界队列），与 Tomcat 请求线程隔离，避免长时间 Agent 任务阻塞 Web 容器
onCompletionSSE 流正常结束时触发：调用 emitter.complete()，保存会话最终状态和 Trace，释放线程资源回池
onTimeoutSseEmitter(300_000L) 超时触发：发送超时提示事件，标记会话为 TIMEOUT，中断当前 Agent Loop，释放线程
onError连接异常或客户端断开时触发：捕获异常写入会话错误记录，emitter.completeWithError() 收尾，释放线程资源
客户端断开通过 SseEmitter.onCompletion() 回调感知客户端断开；调用 agentRuntime.cancel(sessionId) 中断当前 Agent Loop，设置中断标志位，当前 Step 完成后停止不再进入下一步
资源释放断开/超时/错误统一资源清理：释放 ThreadLocal（如 ToolContext 中的 userId），失效会话级缓存 key，写最终 Trace 快照，移除内存中的运行中会话标记
并发保护同一 session 同一时间只允许一个 Agent Loop 运行，通过数据库行锁或分布式锁（Redis 场景）防止重复执行

PART 05Agent Runtime 设计

5.1 架构模式：单主控 Agent + 分层工具 + 可并行执行

CareerMate V2 采用"单主控 Agent + 分层工具系统 + 可并行工具执行"架构。Agent 决策链路保持线性以保证状态一致性；工具执行层可以并行，例如岗位检索、简历读取、JD 上下文读取、多个岗位匹配可以并发执行。

Multi-Agent 不进入 V2，仅作为 Roadmap 预留方向。

5.2 Agent Loop

用户输入 → ① Observe 读取会话状态、用户画像、任务进度 → ② Plan LLM 生成结构化计划摘要（步骤序列 + 工具选择） → ③ Act 通过 Tool Registry 执行工具调用（支持并行、超时、重试、降级） → ④ Observe 读回工具结果（含并行结果聚合） → ⑤ Decide 判断：继续执行 / 需要更多信息 / 可以回复 → ⑥ Respond 生成回复 + UI Action 建议

5.3 工程约束

约束值说明
单次请求最大步数20 步每次用户请求（或单次任务）上限 20 步，超出终止当前任务，不影响后续
每轮最大工具调用5 次超过则强制进入 Respond 阶段
单工具超时30s（可配置）超时返回降级结果
工具失败重试1 次失败后重试一次，再失败走降级
降级策略返回已知上下文工具不可用时用缓存或用户画像兜底
Agent 状态持久化每步落库刷新页面后恢复执行进度
并行执行Act 阶段内同一 Plan 步骤内的无依赖工具可并行执行
最终回答约束必须标注依据标明来源于工具结果、用户上下文，或明确标注为建议

5.4 Agent Trace

每一步执行生成 Trace。前端展示意图、计划摘要、工具调用和结果，不暴露模型内部推理原文。

展示：当前意图 · 计划摘要 · 工具调用及耗时 · 工具结果摘要 · 任务状态 · 下一步建议 不展示：模型内部长推理原文 · Chain-of-Thought 完整输出 · 原始 Prompt 内容

类职责

PART 07MCP Adapter 设计

V2 不要求实现完整 MCP (Model Context Protocol) 平台，但架构层面需要清晰预留扩展点。内部 Tool Registry 仍然是 CareerMate 的主工具系统，MCP 作为外部集成通道。

7.1 设计原则

  • 内部 Tool Registry 是工具权威来源，MCP 不替代它
  • MCP Server Adapter：后续可把 CareerMate 的部分工具暴露为 MCP Tools，供外部 Agent 调用
  • MCP Client Adapter：后续可接入外部 MCP Server（授权外部数据源、公开 API、企业内部系统、用户导入数据），所有外部接入必须在用户授权和法律合规前提下进行
  • V2 只定义接口和扩展点，不引入 MCP 运行时依赖，不影响 MVP 部署复杂度
  • MCP 是 Roadmap 扩展能力

7.2 接口预留

// MCP Server Adapter — 将内部工具暴露为 MCP Tools public interface McpServerAdapter { List<McpTool> listTools(); McpToolResult callTool(String toolName, Map<String, Object> args); void start(); void stop(); } // MCP Client Adapter — 调用外部 MCP Server 的工具 public interface McpClientAdapter { void connect(String serverUrl); List<McpTool> listRemoteTools(); McpToolResult callRemoteTool(String toolName, Map<String, Object> args); void disconnect(); } // V2 实现：NoOp 占位 NoOpMcpServerAdapter implements McpServerAdapter // 所有方法返回空 NoOpMcpClientAdapter implements McpClientAdapter // 所有方法返回空

8.2 MemoryStore 抽象与 MemoryCache 加速层

MemoryStore 是权威持久化存储抽象，以 PostgreSQL 为唯一权威数据源。Caffeine 和 Redis 是 MemoryCache 加速层，属于独立的缓存抽象，不实现 MemoryStore 接口，不承载权威数据：

// MemoryStore — 权威持久化存储（仅 PostgresMemoryStore 实现） public interface MemoryStore { void save(String key, Object value); void saveWithTtl(String key, Object value, Duration ttl); <T> T get(String key, Class<T> type); void delete(String key); } PostgresMemoryStore implements MemoryStore // V2 唯一权威 MemoryStore 实现 // MemoryCache — 缓存加速层（Caffeine / Redis），不实现 MemoryStore public interface MemoryCache { void put(String key, Object value, Duration ttl); <T> T get(String key, Class<T> type); void evict(String key); } CaffeineMemoryCache implements MemoryCache // 本地热点缓存 (L1)，默认启用 RedisMemoryCache implements MemoryCache // 分布式缓存 (L2)，V2 可选 CompositeCache // L1 Caffeine + L2 Redis 两级缓存

读写路径：读 → 查 Caffeine L1 → 未命中查 Redis L2（如有）→ 未命中查 PostgresMemoryStore → 回填缓存。写 → 写 PostgresMemoryStore（权威）→ 失效对应缓存 key。缓存不可用不影响服务，退化到直接读 PostgresMemoryStore。

敏感字段脱敏Trace 日志中姓名/电话/邮箱自动替换为占位符
日志不保存简历原文应用日志仅记录文件名和解析状态，不写入简历原文或 parsed_content 完整内容
Trace 只保存摘要Agent Trace 中不保存简历/JD 完整原文，仅保留结构化摘要（技能标签、工作年限、目标岗位）和脱敏字段
评测样本不含隐私原文agent_eval_cases 中的 resume_context 使用匿名化合成数据，不存储真实用户简历
避免长文本注入 Prompt使用摘要和结构化画像，不把完整简历长期注入 Prompt

PART 09Prompt 模板与版本管理

Prompt 不写死在代码里。核心模板可配置、可审计、可演进。Prompt 变更不应要求重新部署。

9.1 设计

  • System Prompt 按任务类型拆分：简历分析、岗位匹配、面试题生成、回答评估、看板汇总
  • Tool Description 统一规范：名称、用途、参数说明、返回值格式
  • Few-shot 示例可配置，存储在 prompt_versions 中
  • Prompt 模板支持版本号（v1, v2, ...）和状态（draft / active / archived）
  • Prompt 修改可回滚：通过激活历史版本实现
  • 运行时按 task_type 查询当前 active 版本注入

9.2 表设计

表名说明核心字段
prompt_templatesPrompt 模板定义id, template_key, task_type, name, description, current_version_id, status, created_at, updated_at
prompt_versionsPrompt 版本快照id, template_id, version, system_prompt, tool_prompt, few_shot_examples(JSONB), change_log, status(draft/active/archived), created_at

9.3 Prompt 渲染流程

AgentRuntime.plan() → PromptService.render(templateKey, context) → 查询 prompt_templates WHERE template_key = ? AND status = 'active' → 查询 prompt_versions WHERE id = template.current_version_id → 替换变量: {{user_profile}} {{task_context}} {{tool_list}} {{few_shot}} → 注入 Tool JSON Schema 列表 → 返回完整 System Prompt → 发送给 LlmClient

PART 11Agent Evaluation 评测体系

Agent 评测体系用于量化 Agent 质量、对比模型效果、验证 Prompt 改动、发现回归问题。每次修改 Prompt、Tool、模型配置后跑评测，用数据驱动迭代。

11.1 评测维度

维度指标计算方式
意图识别准确率intent_accuracy正确识别意图的用例数 / 总用例数
工具选择准确率tool_selection_accuracy选择了正确工具集的用例数 / 总用例数
工具参数正确率tool_param_accuracy参数正确的工具调用数 / 总工具调用数
RAG 命中率rag_hit_rate检索结果包含期望文档的用例数 / 总用例数
回复可用性response_usability人工评分 1-5 分或 LLM-as-Judge 评分
幻觉率hallucination_rate包含虚构信息的回复数 / 总回复数
平均响应耗时avg_latency_ms端到端延迟（从请求到完整回复）
Token 消耗input_tokens / output_tokens单次执行的平均 token 消耗
估算成本estimated_cost基于模型定价的估算成本（元/次）

11.3 评测流程

① 准备评测用例 (agent_eval_cases) ② 创建评测 Run → 选择模型 + Prompt 版本 ③ 逐条执行：发送 user_input 到 Agent → 记录 Trace ④ 自动比对：意图/工具/参数 vs 期望值 ⑤ LLM-as-Judge 评分：可用性 + 幻觉检测 ⑥ 汇总报告：各维度得分 + 对比历史 Run

12.1 指标采集

指标说明存储位置
total_latency_ms端到端延迟，从用户请求到完整 SSE 流结束agent_sessions

error_code错误码（如有）agent_sessions / agent_tool_calls

  • Actuator 端点（/actuator/metrics, /actuator/health）暴露 JVM 和业务指标
  • 可通过 Micrometer 对接 Prometheus + Grafana
  • agent_sessions 和 agent_tool_calls 表本身可作为成本分析和性能监控的数据源
  • 日志格式统一为 JSON，方便后续接入 ELK / Loki
