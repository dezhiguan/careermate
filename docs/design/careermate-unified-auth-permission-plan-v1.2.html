0. v1.2 修订摘要

v1.1 → v1.2 协议级闭环：本次修订只动协议层，不破坏 v1.1 已定的整体结构。
编号修订点影响章节原因
A1 Token Exchange 强制客户端认证（mTLS / private_key_jwt / client_secret） §3 §7 §12 §13 否则任何拿到用户 access_token 的人都能换下游 token，单 aud 隔离失效。
A2 Consent 撤销实时传播：Auth Gateway 推送撤销事件，RAGForge 维护短缓存 + jti 黑名单 §10 §12 §13 Agent/MCP 风险等级高于普通用户访问，5-15 分钟自然过期不可接受。
A3 Consent vs ACL 边界澄清：明确两者职责、生效顺序、合取规则 §9 §10 v1.1 两套权限并存但未划定边界，实施时会引发"该写哪里"的困惑和漏洞。

1. 核心结论

最终边界：Auth Gateway 负责统一认证和 token 签发；CareerMate 是求职业务归属与授权 Source of Truth；RAGForge 是独立多租户 RAG 平台与 KB 权限执行端；Agent/MCP 必须通过受限 delegation 访问资源。
Auth Gateway

统一登录、IDP 验签、JWT 签发、refresh rotation、登出、JWKS、token exchange、delegation token、风险控制。

v1.2：token exchange 与 delegation 端点强制客户端认证；新增 consent 撤销事件推送能力。

CareerMate

管理用户、个人租户、角色、业务资源、套餐额度、RAG KB 业务绑定。

修订：不再给 RAGForge 传可被信任的 X-User-Id；下游从已验签 token 读取 principal。

RAGForge

管理知识库、文档、chunk、embedding、检索、评测、KB ACL、审计日志。

v1.2：权限判定 = ACL（静态）∩ Consent（用户授权，若调用方为 Agent/MCP）∩ Token Scope。

2. 第一版用户、租户、角色关系

第一版不做企业角色，不做团队 KB，不做跨租户共享。只保留 USER、ADMIN、SERVICE_ACCOUNT，再通过 principal_type 区分 user、service_account、agent、mcp_client、job。

租户模型

租户类型tenant_id展示 slug说明

PLATFORM platform 或固定 UUID platform 平台公共资源空间：公共 JD KB、公共面试 KB、系统配置、同步任务、服务账号。

角色模型

字段取值含义
principal_type user / service_account / agent / mcp_client / job 区分调用主体类型，不再把人类角色和服务主体混在 roles 里。

scopes cm:read、cm:write、rag:search 等 动作级授权，token exchange 和 delegation 时必须裁剪到最小范围。

3. Auth Gateway 职责

认证能力

  • 手机号验证码、密码、第三方 IDP、企业 SSO 统一入口。
  • IDP token 验签：issuer、audience、nonce、过期时间、公钥 kid。
  • 签发单 aud access token、refresh token、service token、delegation token。
  • token exchange：后端用上游 token 换下游单 aud token。
  • JWKS 发布、密钥轮换、token introspection、userinfo。
  • v1.2：OAuth Client Registry：管理 CareerMate 后端、Agent Runtime、MCP Server 等 confidential client 凭证。
  • v1.2：Consent 撤销事件推送：通过 Webhook / 消息队列分发到下游资源服务。

运行安全

  • 风险控制：登录限流、暴力破解防护、异地登录告警。
  • 密钥管理：JWT 私钥、service token key、client_secret 存放在 KMS / Vault；开发期可用受限文件。
  • CSRF：Cookie 登录流必须启用 SameSite、Origin 校验和 CSRF token。
  • PII 脱敏：手机号、简历、邮箱、用户画像不得明文写普通日志。

JWKS 轮换策略

  • 双 kid 并存窗口不少于 24 小时。
  • 下游服务 JWKS 缓存 1 小时；遇到未知 kid 主动回源拉取一次。
  • 新 token 用新 kid 签发后，旧 kid 保留到所有旧 access token 与缓存窗口过期。

风险控制 SLO

场景策略
单账号登录失败5 分钟 5 次失败，锁定 30 分钟或要求二次验证。
单 IP 登录突增1 分钟 30 次登录请求，触发图形验证或临时限流。
refresh token 重放吊销整个 token family，记录高危审计。
异地/新设备登录记录风险事件，必要时短信或站内通知。
token exchange 客户端认证失败立即拒绝并记录高危审计；连续失败触发该 client 临时停用。

4. Token 设计

必须修：access token 的 aud 必须是单值。禁止一张 token 同时访问 careermate-api、ragforge-api、mcp-api。

Token 类型

Tokenaud用途有效期是否给前端
access_token careermate-api 或单一目标服务 用户访问当前业务 API。 ≤ 15 分钟 是
refresh_token auth-gateway 刷新 access token，只给 Auth Gateway 使用。 7-30 天，滑动过期 HttpOnly Cookie 或安全存储

service_token 指定服务 服务账号调用，不代表具体用户。 短期；长期凭证仅用于换短 token 否

6. 登录、刷新、登出与 session_version

1. 登录
客户端到 Auth Gateway 登录或提交 IDP token。
2. 建用户
Auth 创建用户身份，CareerMate 创建个人租户。
3. 签发
签发 aud=careermate-api access token 和 refresh token。
4. 访问
CareerMate 本地验签；需要 RAG 时执行 token exchange。
5. 刷新/登出
refresh 时校验 session_version；登出吊销 token family。

session_version 规则

  • 下游服务只验签 access token，不每个请求查 session_version。
  • access token 有效期 ≤ 15 分钟，依靠短过期收敛权限变更。
  • refresh 时 Auth Gateway 校验 session_version、用户状态、session 状态。
  • 封禁、改密、全端登出等强即时动作：写 Redis JTI 黑名单，并吊销 refresh token family。

注册与租户创建补偿

  • 推荐同步创建：Auth Gateway 创建 user 后调用 CareerMate 创建 personal tenant；成功后才完成登录。
  • CareerMate 创建失败时，Auth Gateway 标记用户为 PENDING_PROFILE，返回可重试错误，不签发业务 token。
  • 后台补偿任务扫描 PENDING_PROFILE 用户并补建租户。

7. Token Exchange v1.2 改

v1.2 强化：token exchange 端点必须执行双重认证——既验 subject_token，也验调用方客户端身份。仅有用户 access_token 不足以换取下游 token。

7.1 客户端注册

所有有权调用 token exchange 的服务必须在 Auth Gateway 注册为 confidential OAuth client，获取 client_id 与凭证。

client_id 示例归属允许的 grant_type允许的 requested_audience
careermate-backend CareerMate API 服务 token-exchange、client_credentials ragforge-api、mcp-api
careermate-agent-runtime Agent 编排服务 token-exchange、delegation-token ragforge-api
mcp-gateway MCP Server 入口 delegation-token ragforge-api

7.2 客户端认证方式（任选其一，按等级递增）

方式适用环境说明
client_secret_basic 开发期、内网 HTTP Basic 携带 client_id:client_secret；secret 必须存 KMS / Vault。
private_key_jwt 生产推荐 客户端用本地私钥签发短期 JWT 作为 client_assertion；Auth Gateway 通过预登记的客户端公钥验签。无 secret 落地泄漏风险。
mTLS 对内服务、高敏感链路 双向 TLS；client 证书由内部 CA 签发。可与 private_key_jwt 叠加使用。

7.3 完整流程

Web Client
  -> CareerMate API: Authorization: Bearer aud=careermate-api
CareerMate API (client_id=careermate-backend)
  -> Auth Gateway /oauth/token-exchange:
       # 客户端认证
       Authorization: Basic base64(client_id:client_secret)
       # 或 client_assertion=<private_key_jwt>
       # 或 mTLS 客户端证书
       # 业务参数
       subject_token = user access token
       subject_token_type = urn:ietf:params:oauth:token-type:access_token
       requested_audience = ragforge-api
       requested_scopes = rag:search
       resource = kb_resume_26
Auth Gateway
  -> 校验客户端身份（client_secret / JWT 签名 / mTLS 证书）
  -> 校验 subject_token（验签 + aud=careermate-api + 用户状态）
  -> 校验该 client_id 允许换取 requested_audience
  -> 裁剪 scope 至 client 允许范围 ∩ 用户已有 scope
  -> 返回 exchanged_token aud=ragforge-api
CareerMate API
  -> RAGForge: Authorization: Bearer exchanged_token

7.5 Auth Gateway 必须校验

  • 客户端身份合法且未停用。
  • 该 client_id 在白名单允许换取的 requested_audience 内。
  • subject_token 验签通过、aud=careermate-api、未过期、用户状态正常。
  • 用户拥有 requested_scopes 的上游权限；最终 scope = client 允许 ∩ 用户已有，禁止扩权。
  • CareerMate 在发起 exchange 前必须先判断用户是否拥有该业务资源（owner / binding 校验）。
禁止：任何无客户端认证的 token exchange 请求；任何把上游 scope 原样透传到下游 token 的实现。

8. CareerMate ↔ RAGForge 状态同步

明确 SoT：CareerMate 是业务资源归属 Source of Truth；RAGForge 是 KB ACL 执行 Source of Truth。二者通过领域事件同步，并用日级对账发现漂移。
事件触发方RAGForge 动作
user.deletedCareerMate撤销该用户 personal KB ACL，停止检索，按数据保留策略删除或冻结文档。
user.disabledCareerMate拒绝该用户相关 delegation 和 KB 查询。
rag.binding.createdCareerMate创建或更新 KB 归属、owner、visibility、ACL。
rag.binding.revokedCareerMate撤销对应 KB ACL，拒绝后续检索。
plan.downgradedCareerMate降级 KB 额度、禁用高级检索或写入能力。

对账任务

  • 每日比对 rag_kb_bindings 与 RAGForge knowledge_bases / kb_acl。
  • 发现 owner、tenant、visibility、状态不一致时生成告警和修复任务。
  • RAGForge 检索时仍做实时权限校验，不能只依赖同步正确。

9.1 KB 可见性

9.2 权限判定公式 v1.2 新

RAGForge 每次访问都执行：
allow = Token.valid ∧ Token.scope ⊇ required_scope ∧ ACL.permits(principal, kb, action) ∧ (principal_type ∉ {agent, mcp_client} ∨ Consent.permits(delegated_user, principal, kb, action))

三层判定的语义如下：

层检查内容来源
1. Token 验签、aud、过期、scope、jti 黑名单。 JWT claims + Redis 黑名单
2. ACL（静态权限） principal 对 KB 是否有 read / write / admin 权限。
对 user：检查 owner / visibility / kb_acl。
对 service_account：检查 kb_acl 中的显式条目。		 RAGForge kb_acl 表 + KB 自身 owner/visibility
3. Consent（动态授权，仅 agent / mcp_client） 校验调用方是否被 delegated_user 显式授权访问此 KB 与此 action。 RAGForge 本地 consent 缓存（订阅自 Auth Gateway）

9.3 RAGForge 每次检索必须执行

  • 验签 JWT，校验单一 aud=ragforge-api。
  • 从 token claims 提取 principal_type、user_id、tenant_id、scopes、allowed_kb_ids、delegated_user_id、consent_id。
  • 校验 scope 包含 rag:search。
  • 校验目标 KB 在 allowed_kb_ids 内，或符合 PUBLIC / owner / SYSTEM 规则。
  • 对静态权限查 kb_acl + KB owner/visibility。
  • 若 principal_type 是 agent / mcp_client：查本地 consent 缓存，校验 consent_id 仍有效且涵盖此 KB 与 action。
  • 向量检索和 chunk 查询必须附加 tenant、kb、visibility 过滤条件。
  • 写审计日志，记录 principal、delegated user、kb、scope、consent_id、结果数量、耗时。

10. Agent / MCP Delegation v1.2 改

必须修：delegation token 必须由 Auth Gateway 签发。Agent/MCP 首次代表用户访问 RAGForge 时必须有 consent 记录，RAGForge 只通过 JWKS 验签和 claims 校验，不信任调用方自报。

10.1 Consent vs ACL：职责边界 v1.2 新

Consent 和 ACL 不是替代关系，而是合取关系：一个 Agent 请求被放行的前提是 它本身有 ACL 权限，且 它代表的用户给它了 consent。
对比项ACLConsent
授权对象 principal（user / service_account / agent / mcp_client）对 KB 的静态权限 用户对 agent / mcp_client 的动态授权
授权方 平台管理员、KB owner（CareerMate 后端触发同步） 普通用户本人（前端 consent 流程）
生命周期 长期；显式增删 短期；用户可随时撤销；可设过期
存储位置 RAGForge kb_acl 表 Auth Gateway agent_consents 表 + RAGForge 本地缓存
典型场景 "careermate-agent 服务账号有权读 PUBLIC_JD 类型的所有 KB" "user:26 授权 careermate-agent 在 30 天内代表自己访问 kb_resume_26"
RAGForge 判定时机 每次请求 每次请求（仅当 principal_type 为 agent / mcp_client）
若仅有一方通过 仍拒绝 仍拒绝

10.5 Consent 撤销实时传播 v1.2 新

问题：delegation token 有效期 5-15 分钟，单纯靠自然过期不足以保障 Agent/MCP 场景的撤销时效（用户撤销后到 token 过期前的窗口内，Agent 仍能访问私密 KB）。

方案：三层防御组合，撤销在 60 秒内全链路生效。

层机制时效
1. 阻断签发新 token Auth Gateway 撤销 consent 后，/oauth/delegation-token 立即拒绝同 consent_id 的换取请求。 立即生效
2. 推送撤销事件 Auth Gateway 通过 Webhook / 消息队列把 consent.revoked 推送给 RAGForge 及其它资源服务，事件含 consent_id、jti_list（可选）。 ≤ 5 秒（同集群内）
3. RAGForge 本地校验 RAGForge 维护 consent 缓存（TTL ≤ 60s）和 jti 黑名单（保留至 token exp）；每次检索查这两者。订阅事件后立即更新缓存。 ≤ 缓存 TTL（最坏 60 秒）

事件结构

POST {subscriber}/events/consent-revoked
Authorization: Bearer <service_token aud=subscriber>
X-Event-Signature: <HMAC of body>

{
  "event_type": "consent.revoked",
  "event_id": "evt_xxx",
  "occurred_at": 1781760000,
  "consent_id": "consent_xxx",
  "user_id": 26,
  "client_principal_id": "careermate-agent",
  "active_jtis": ["jti_delegation_xxx", "jti_delegation_yyy"]
}
  • 事件签名用 HMAC 防伪造；订阅方必须校验签名后才更新本地状态。
  • 事件投递必须至少一次（at-least-once），订阅方按 event_id 幂等去重。
  • RAGForge 启动时主动拉取最近 24h 的 active consent 全量快照，避免事件丢失导致漂移。
  • 兜底：若事件通道异常，缓存 TTL 60s 仍能限制最大暴露时间。

10.6 用户视角

  • 用户在 CareerMate 设置页可查看已授权的 Agent / MCP Client 列表（来自 Auth Gateway /oauth/consents）。
  • 撤销操作前端 → CareerMate → Auth Gateway POST /oauth/consents/{consent_id}/revoke，撤销后立即返回成功，并异步触发 §10.5 的传播流程。

11. 服务间调用规范

必须遵守：安全主体信息只能来自已验签 token。X-User-Id、X-Tenant-Id、X-User-Roles 不能作为鉴权依据。

允许的 Header

Authorization: Bearer <single-aud-token>
X-Request-Id: req_xxx
X-Trace-Id: trace_xxx

禁止作为权限依据的 Header

X-User-Id: 26
X-Tenant-Id: tn_xxx
X-User-Roles: USER
X-Delegated-By: careermate-backend

这些字段如果需要排查可以写入日志，但不能参与鉴权。鉴权必须读取 JWT claims。

14. 分阶段落地 v1.2 微调

阶段目标验收标准
P0 协议定稿：单 aud、token exchange（含客户端认证）、claims 拆分、禁止 principal header、session_version 路径。 伪造 aud、复用下游 token、header 冒充用户、无客户端认证的 token exchange 均被拒绝。
P1 Auth Gateway 上线：登录、刷新、登出、JWKS 轮换、风控、CSRF、密钥管理、oauth_clients 注册。 refresh rotation 生效；登出后 refresh 不可用；未知 kid 可回源刷新 JWKS；private_key_jwt 客户端认证通过端到端联调。
P2 CareerMate 租户与 RAG 绑定：独立 tenant_id、rag_kb_bindings、领域事件。 用户注销、禁用、解绑后，RAGForge 权限状态能同步并可对账。
P3 RAGForge 权限执行：KB ACL、检索过滤、三层判定（Token + ACL + Consent）、审计字段扩充。 跨用户个人 KB 检索、写公共 KB、SYSTEM KB 前端访问均被拒绝。
P4 Agent/MCP delegation：consent、delegation token、consent 撤销事件推送 + RAGForge 缓存 + jti 黑名单。 Agent/MCP 只能查用户授权 KB；撤销 consent 后≤ 60 秒内全链路不可用，已签发 token 写入 jti 黑名单。
P5 管理后台。 可管理用户状态、管理员角色、服务账号、公共 KB、授权记录和审计日志。

15. 第一版非目标

  • 企业租户、ORG_ADMIN、ORG_MEMBER、团队 KB。
  • 跨租户共享 KB。
  • DPoP / mTLS token binding（与服务间 mTLS 不冲突；这里指用户 token 设备绑定）。
  • 完整 OAuth 第三方开放平台。
  • 长期 API Key 不给普通用户开放；如需给第三方系统，必须走 service account + 短 token 交换。

16. 必须避免的错误

  • 一张 access token 同时包含多个 aud。
  • RAGForge 只凭 kbId 放行检索。
  • 下游服务信任 X-User-Id、X-Tenant-Id 等 principal header。
  • refresh token 不轮换，泄漏后无法发现重放。
  • Agent/MCP 没有 consent 就代表用户检索私有 KB。
  • RAGForge 检索不加 tenant / kb / visibility 过滤条件。
  • 管理员默认可以直接读取用户简历、个人 KB。
  • 审计日志记录明文手机号、简历正文或完整 prompt。
  • Token exchange / delegation-token 端点不做客户端认证，仅凭 subject_token 放行。
  • Consent 撤销后只靠 token 自然过期，不通知下游资源服务。
  • 把 user → agent 的 consent 写到 RAGForge 的 kb_acl 表里（应该写到 Auth Gateway 的 agent_consents）。
