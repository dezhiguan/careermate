1. 背景与问题（为什么做）

近期评估了一类本地文件优先、CLI 无关的开源求职流水线方案的简历生成设计，与 CareerMate 现有实现做了逐轴对照。两套系统哲学相反：

  • 业界开源方案：无上传冷启动、单个 Markdown 文件即真源、确定性脚本做事实核对。
  • CareerMate：强制上传简历、结构化落库（ResumeEntity + ResumeVersionEntity）、多 Agent（Writer/Critic）辩论校验。

对照后识别出三处可优化项。其中两处直接影响新用户转化与输出可信度，为本方案重点；第三处为体验增强项，优先级较低。

对照中发现的两处现状缺口（本方案待验证前提）：
  • 职业画像 CareerProfile（含真实 targetRole / skillKeywords / seniority）当前未接入简历生成链路，一个真实信号源被闲置。
  • Writer/Critic 辩论在达 MAX_ROUND（默认 5 轮）未收敛时会「输出最后草稿并落库」；且 CriticVerdict 解析失败返回中立分 0.5。全链路依赖 LLM 判断真实性，缺少字符串级的确定性事实兜底，存在「看起来真实的编造稿蒙混落库」的风险窗口。

实施前置动作：上述两处结论来自代码走查，实施 P1/P2 前需由研发在最新分支复核对应文件（见附录锚点），确认行为未变更后再动工。

2. 现状三轴对照

轴一 · 简历真源

维度业界开源方案CareerMate（现状）
「上传」步骤无。冷启动由 AI 从粘贴/LinkedIn/口述写入 Markdown 文件强制。简历为空即 BizException(400,"请先上传简历")
真源载体单个可 diff 的 Markdown 文件ResumeEntity（Tika 解析入库）+ 多版本 ResumeVersionEntity
新用户门槛零，无简历也能开始硬门槛，必须先有文件

轴二 · 版式渲染

维度业界开源方案CareerMate（现状）
渲染路径Markdown → HTML/LaTeX 模板 → 浏览器/pdflatexMarkdown → ResumeStructureParser → iText(PDF)/POI(Word)
版式定义外置模板文件，换风格只改模板硬编码在 Renderer（A4/边距/字体链均写在 Java 内）
中文/服务端确定性弱（无中文字体处理，依赖浏览器较重）强（字体探测、Emoji 去污、表格转 bullet）

结论：渲染引擎本身 CareerMate 更工程化，不动 iText/POI。仅将版式抽象为可配置模板并内置两套开箱版式（见 P3），补齐「换风格需改代码」的短板。

轴三 · 防编造护栏

维度业界开源方案CareerMate（现状）
机制Prompt 边界 +「关键词只重组不捏造」+ 确定性事实校验脚本四层：FabricationRiskDetector 拦截 → Writer 硬约束 → ResumeCritic 评审 → 占位词检测
哲学确定性事实核对LLM 判断真实性为主
整体强度轻重（多 Agent 辩论，明显更强）

结论：CareerMate 这块整体更强，唯一短板是缺确定性兜底——即业界开源方案用一个确定性脚本就做到的事实核对。P2 即补此短板。

3. 优化目标与范围

目标
① 消除新用户「无简历文件即无法开始」的转化门槛；② 为 LLM 判断补一道确定性事实底线；③ 内置多套导出模板；④ 打通简历就地编辑闭环。
范围内
简历生成工作流（resume/version/workflow）、冷启动建档、事实校验 Gate、导出模板配置层、对话内就地编辑面板（复用已有版本编辑接口）。
范围外
不改 iText/POI 渲染引擎；不改多 Agent 辩论收敛算法本身；不引入 pgvector 等基础设施变更。
兼容性
保持现有「上传→生成」主链路不变；新增能力以旁路/新增 Gate 形式接入，不破坏 ResumeEntity/ResumeVersionEntity 结构。

4. P1 · 无上传冷启动建档（三级降级阶梯） 高优先级

问题

新用户无简历文件时被 stepLoadResume() 的 400 硬门槛挡住，直接流失；同时已采集的真实画像 CareerProfile 未被利用。新用户「有多少信息」参差不齐——从「口述了一堆经历」到「什么都不填、只想先看到一份简历」——单一路径覆盖不了。

方案：按用户已有信息量三级降级，任何情况下都能产出一份简历

层级用户已提供生成策略
L1口述 / 粘贴片段 / LinkedIn 等真实信息LLM 基于真实信息生成初版 ResumeEntity（origin=COLD_START）
L2仅有画像 CareerProfile（目标岗位/技能等）用画像预填结构，其余章节留引导占位
L3什么都没有产出系统默认骨架简历：默认格式 + 标准章节 + 引导占位，状态标 DRAFT_SKELETON，直接进 Canvas（P4）待填

核心约束（不可动摇）：所谓「默认内容」只能是章节结构 + 填写引导，绝不预置任何虚构的公司/学历/经历。L1/L2 写入的内容也只允许来自用户本次对话明确提供或 CareerProfile 已存在的事实，不得凭空补全。此约束与 P2 事实 Gate 天然衔接。

护栏冲突提示（必须处理）：P2 的质量校验会拒绝含「待补充/示例/XXX」占位词的简历，而 L3 骨架天然含占位。解法：为骨架引入独立状态 DRAFT_SKELETON——豁免占位词检测，但导出/投递前强制校验「已离开骨架状态」（占位是否填充完成）；未完成只能导出带「草稿·未完成」水印或直接禁止投递。既能「啥都没有也先出一份」，又杜绝半成品当真简历投出去。

验收标准

  1. L1：无简历账号提供 3 段真实经历 → 初版仅含用户提供 + 画像已有事实，无凭空补全，origin=COLD_START、status=READY。
  2. L2：仅有画像时生成 → 画像字段被预填，其余为引导占位。
  3. L3：什么都不提供也能拿到默认骨架简历，status=DRAFT_SKELETON，且不含任何虚构公司/学历/经历。
  4. 护栏：DRAFT_SKELETON 未填完即导出 → 带「草稿·未完成」水印或被拦截；填充完成转 READY 后正常导出。
  5. 存量「上传→生成」链路回归无影响（origin 默认 UPLOAD、status 默认 READY）。

5. P2 · 确定性事实校验 Gate 高优先级

问题

全链路靠 LLM 判断真实性；MAX_ROUND 未收敛仍落库、CriticVerdict 解析失败给中立 0.5，缺字符串级确定性兜底。占位词检测挡得住「公司A/XXX」，挡不住「某大厂真实感项目」。

方案

在工作流第 6 步 QUALITY_CHECK 内新增一道不可绕过的确定性 Gate（即业界开源方案「确定性事实核对」哲学）：从生成版本抽取强事实，逐条比对源 ResumeEntity + CareerProfile，源中无支撑者判为可疑。

校验对象（强事实）

  • 公司/机构名、学历与院校、证书名称、职称/头衔
  • 量化数字（金额、百分比、规模、年限）——要求在源文本中有可对齐的出处

判定与动作

命中情况动作
强事实全部有源支撑通过，正常落库
存在无源强事实拒绝自动落库；在返回卡片标红「疑似无出处：{列表}」，要求用户确认来源或移除后再存
解析异常fail-closed：视为未通过，走人工确认，不静默放行

字段设计

  • ResumeVersionEntity.factCheck（新增，JSON）：{status: PASS|SUSPECT|ERROR, unsourcedFacts:[...], checkedAt}，作为可信度可审计凭证。
  • 校验器独立成 ResumeFactVerifier（确定性、无 LLM 调用），便于单测与复用。

影响文件（待研发复核后修改）

  • resume/version/workflow/GenerateResumeWorkflowRunner.java（QUALITY_CHECK 内挂载 Gate）
  • resume/version/verify/ResumeFactVerifier.java（新增，确定性抽取+比对）
  • resume/version/entity/ResumeVersionEntity.java（新增 factCheck 字段 + 迁移）

验收标准

  1. 构造一份含源简历中不存在的「腾讯 3 年经历」的生成稿 → Gate 判 SUSPECT，不落库，卡片标红列出该条。
  2. 正常重组真实经历的生成稿 → Gate PASS，正常落库，factCheck.status=PASS。
  3. 校验器抛异常时 → fail-closed 走人工确认，无静默放行。
  4. Gate 为确定性逻辑，同一输入多次运行结论一致（可重放）。

6. P3 · 内置简历模板（PDF 精排版 + Word ATS 版） 中优先级

问题

版式参数（A4/边距/字号/字体链/章节样式）硬编码在 ResumeVersionPdfRenderer/DocxRenderer，换风格需改代码重编译；且当前只有一种版式，无法针对「给人看」与「过 ATS 机器解析」两类投递场景分别优化。

方案

内置两套开箱模板，导出时由用户选择；版式参数抽成 ResumeLayoutProfile 配置，Renderer 从配置读取而非写死。不改渲染引擎本身，iText/POI 保持不动。

  • PDF 精排版（iText 渲染）：居中抬头、品牌色分节线、排版精致，用于直接投递 / 企业邮箱附件 / 给人看。
  • Word · ATS 友好版（POI 渲染）：单栏、纯黑、衬线、无图形无颜色，最大化机器可解析度，用于投递 ATS 系统或需二次编辑的场景。

7. P4 · 简历就地编辑（对话内 Canvas） 高优先级

问题

AI 生成的简历用户常想微调（改一句措辞、补一条经历、删一段）。当前只能「重新生成」或「下载后用外部工具改」，改完无法回流到系统版本，再次导出仍是旧内容——编辑闭环断了。

方案

在对话内提供 Canvas 可编辑面板（即用户截图中 ChatGPT 的「写作」面板交互）：面板加载版本的 contentMarkdown，用户就地编辑，失焦/停顿后自动保存，保存后再导出即编辑后版本。桌面端可另提供独立 md 编辑页作补充。

利好：后端闭环已具备，几乎零新增接口。 经代码走查，ResumeVersionController 已有：
  • GET /{versionId} → 取 contentMarkdown 载入编辑器
  • PUT /{versionId} → updateVersion() 直接 setContentMarkdown() 落库（即「保存」）
  • GET /{versionId}/export/pdf|docx → 从同一版本实体渲染 → 保存后再下载天然是改后版

因此 P4 主体工作量在前端：Canvas 面板组件 + 自动保存（防抖）+ 保存态提示。后端仅按下方决策选做小幅增强。

待拍板决策（请审核时选定）

决策 ① · 手工编辑是否也过事实校验？
✓ 定稿（2026-07-14）：采用 A · 保存时轻量提示不拦截
A 保存时做轻量事实校验，仅提示不拦截：新增的强事实若在原简历无出处，标黄提醒「确认属实?」，用户可忽略。✓ 已选定
B 完全放开：用户编辑自己的简历，尊重自主，不做任何校验。（未采用）
决策 ② · 编辑的版本语义
✓ 定稿（2026-07-14，V1.5 改判）：采用 B · 编辑 fork 新版本，保留可追溯
A 原地覆盖 contentMarkdown（现有 PUT 行为，最简单）。缺点：手改覆盖 AI 原版、不可回溯。（未采用）
B 编辑时 fork 出新版本，标 origin=MANUAL_EDIT，保留「AI 生成版 vs 手改版」可追溯。✓ 已选定

实现要点：首次手工编辑时 fork 一个 MANUAL_EDIT 版本，同一编辑会话后续更新该手改版、不重复 fork；AI 原版始终保留，与多版本产品定位一致。

影响文件

  • 前端 · workspace 简历卡片 → 升级为可编辑 Canvas 组件 + 自动保存（防抖 300–800ms）+ 保存态
  • 后端 · 复用 resume/version/controller/ResumeVersionController.java 的 GET / export；决策②=B：ResumeVersionService 新增 forkVersion()——首次手工编辑 fork 出 origin=MANUAL_EDIT 新版本，后续编辑更新该手改版，AI 原版保留
  • 后端 · 决策①=A：保存路径挂 ResumeFactVerifier（复用 P2 校验器）返回提示项，仅提示不拦截

验收标准

  1. 在 Canvas 改动一句话，失焦后自动保存成功（PUT /{versionId} 200）；刷新页面编辑仍在。
  2. 保存后重新导出 PDF / Word，文件内容含该改动。
  3. 断网/保存失败时给出可重试提示，不静默丢改动。
  4. （决策①）编辑加入原简历无出处的强事实，保存时出现标黄提示且不拦截，用户可忽略后仍能保存。
  5. （决策②）首次手工编辑fork 出 origin=MANUAL_EDIT 新版本，AI 原版仍可见；同会话后续编辑更新该手改版、不重复 fork；再次导出即手改版最新内容。

9. 风险与回滚

风险缓解 / 回滚
P1 建档路径被误用于绕过真实性建档强制走 P2 Gate；sourceSignals 全程审计；仅在无活跃简历时触发。
L3 默认骨架被当真简历投出去DRAFT_SKELETON 状态：豁免占位词检测但导出/投递前强制校验已填充；未完成加「草稿·未完成」水印或拦截；默认骨架只含结构不含虚构事实。
P2 Gate 误报（真实事实判无源）判定为「拒绝自动落库+人工确认」而非「直接删」，用户可确认来源放行；比对规则可配置阈值，先灰度观察误报率再收紧。
实体字段迁移影响存量新增字段均带默认值（origin=UPLOAD、factCheck 可空），存量语义不变；迁移脚本可回滚。
P4 手工编辑绕过防编造护栏决策①=A：保存时轻量校验、仅提示不拦截，兜住无意夸大又不侵犯用户自主。
P4 fork 导致版本膨胀决策②=B 的注意点：仅在首次手工编辑时 fork 一个 MANUAL_EDIT 版本，同一编辑会话后续更新该版本、不每次保存都 fork；AI 原版与手改版并存可对比。
P4 自动保存丢改动 / 并发写保存失败可重试提示、不静默丢；PUT 走用户维度校验，编辑基于最新 GET 版本，避免跨会话覆盖。
对照结论与最新代码偏移实施前置动作强制研发复核附录锚点，行为不符则先对齐再动工。

10. 验收标准（Playwright 端到端）

每项优化除单元测试外，均需以下 E2E 场景通过（延续 CareerMate 现有 Playwright 约定）：

场景 A（P1）：新账号无简历 → 触发从 JD 生成
  期望：进入建档引导；提交经历后生成初版简历；
        断言 origin=COLD_START，且产物不含用户未提供的公司/学历。

场景 B（P2）：注入含无源「大厂经历」的生成稿
  期望：卡片标红「疑似无出处」，无新版本落库；
        断言 factCheck.status=SUSPECT。

场景 C（P2 反例）：真实经历重组稿
  期望：正常落库；断言 factCheck.status=PASS。

场景 D（回归）：存量「上传→生成」全链路
  期望：与优化前输出一致，origin=UPLOAD，无异常。

场景 E（P3）：同一简历分别导出 PDF 精排版 / Word ATS 版
  期望：两份内容一致、版式不同，与预览观感一致；
        Word ATS 版可被主流 ATS 正确解析；默认模板与现状一致。

场景 F（P4）：Canvas 就地编辑 → 自动保存 → 重新导出
  期望：面板改动一句话，失焦后自动保存（PUT /{versionId} 200）；
        刷新页面编辑仍在；重新导出 PDF/Word 含该改动；
        断网时保存失败给可重试提示，不静默丢改动。

合并前置：按既有规范，合入 main 前须 mvn test-compile（非仅 compile）+ 前端 npm build 全部通过；Playwright 用例仅本地验证，不随生产代码提交。
