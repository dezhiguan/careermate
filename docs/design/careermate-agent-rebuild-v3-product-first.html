二、关键架构决策（ADR）

ADR-1 · 底座先行，废弃"多 Agent 先行"

两份 V2 文档在顺序上自相矛盾：roadmap 让多 Agent 排第一、底座垫底；41-day 让底座第一。采纳 41-day 顺序。理由：若在自研 LlmClient 上把 debate/DAG/反思/checkpoint 四套复杂系统建完再"抽空换底座"，等于四套系统全部重接线，返工面积巨大。先把 runtime 迁到 ChatClient/Advisor，后续能力直接长在其上。

ADR-2 · fast-path / deep-path 分层（一级约束·新增）

debate(≤3) × reflection(≤3) × 多 Agent 叠加 → 单次"简历定制"可能 9+ 次 LLM 往返、30–60s+ 延迟、数倍 Token。对"随手一问"的产品是灾难性 UX。强制分层：
· fast-path：单 Agent 直答，覆盖 ~90% 交互，秒级；
· deep-path：仅用户显式触发"深度定制简历 / 模拟面试复盘"才进反思/debate 重管线，并在 UI 明确标注"深度模式（较慢）"。
没有这一层，"技能齐全"会直接反噬"可用"。

ADR-3 · 保留 MCP

MCP 是 2026 最硬的互操作技能之一（RAGForge 侧已做过传输收口）。careermate MCP 模块已可用，保留并作为"agent 对外能力暴露"锚点，不删。

ADR-4 · 复用 CriticAgent，砍消息总线

Writer-Critic 的 Critic 角色已存在。第二段的 debate 直接在现有 supervisor + CriticAgent 上做进程内收敛循环，不引入 AgentMessageBus / Redis pub/sub / A2A @Tool 递归调用这套重装备（5 个 agent 用不上，纯属过度设计）。

ADR-5 · Checkpoint 只做崩溃恢复 + HITL

求职助手里用户几乎不会 fork / time-travel 一次 agent run。只做：deep-path 长任务的崩溃续跑 + "发送简历前"HITL 暂停确认。降级为可选：时间旅行 UI、from-checkpoint fork、前端运行时间轴。

ADR-6 · 迁移从 V29 起 · 表命名避让

新表统一 V29+ 编号；多 Agent 协作表用 agent_collab_* 命名，避免与已存在的 agent_messages 表冲突。
