★ 交互范式 —— 围绕 JD 连续打造简历（对话优先 · 一条主线）

★ 北极星（一句话，覆盖全部） 一切围绕一条 JD 展开：生成简历 → 修改简历 → 导出简历 → 这岗的面试题 → 这岗的薪酬 → 这家公司的氛围——全部在与小职（Agent）的同一条对话主线里完成；小职始终锚在「这条 JD + 这份简历」上，记得聊过什么、不串台、不胡说。
小职的三个保证（直接回应"针对不同 JD 不搞混、不搞错、不胡说"）：
  • 不失忆：记得这条 JD 下聊过什么、你定过什么——整条 JD 会话全量喂入上下文 + 按 JD 作用域隔离（非 20 条截断；会话超长时再滚动摘要）。回来能"延续上次"。
  • 不搞混 / 不搞错：不同 JD 各一条线，隔离的是「对话上下文」（按 JD 作用域，绝不把 A 岗的对话灌进 B 岗）；但资产（简历版本/面试记录/八股）+ 宏观进度 + 长期偏好仍 user 级共享、可显式跨线复用——如"把抖音那份简历改成电商版"。即：隔离对话、共享产出。
  • 不胡说八道：回答/改简历只依据 KB599 的 JD + 你真实简历/长期记忆，Critic 复核，缺的技能明说、不编造。
记忆机制（避免过度设计）：当前 JD 会话全量喂入（超长再滚动摘要）+ 严格按 session 作用域隔离——这解决"不失忆/不搞混"，不为对话连续自建向量库。只有用户长期偏好（如"只想远程""期望35k"）走 pgvector 语义记忆；JD/简历/题库素材走 RAG 检索。
三条交互支撑：① 一条主线、JD 锚定，机会/进度/资产都在同一线内发生不切走；② 能说就不手输，筛选/找资产/看进度/改画像一句话交给小职，不摆表单；③ 模块以内联卡片 / 侧边 Canvas 被召唤进对话，可看可轻点，但由对话驱动。
分寸：对话优先 ≠ 纯文字。列表/画布/图表照样富渲染在对话里，只是召唤与操作都走对话。简历 Canvas（02）是范本。

Agent 能力体现（为什么这必须是智能体，不是编辑器）

若去掉 Agent，本产品退化为"简历编辑器 + 岗位列表"。Agent 能力藏在"说一句就搞定"的背后，与架构组件一一对应：

Agent 能力产品中的时刻架构组件

02 简历定制 —— ★ 产品核心（Agent + Canvas）

护城河 · Agent 驱动 · 全站最精致的一屏 核心诉求 = 「一条 JD → 一份定制简历」，且由小职（Agent）对话驱动——不是脱离对话的表单。JD 来自知识库查询（KB599）。此屏 = 小职对话 + 简历 Canvas：小职读 JD 做 gap 分析、实时改写右侧简历 Canvas，每个改动既能对小职说、也能在 Canvas 上点。深度定制走 deep-path（简历 specialist + Critic 复核，缺失项不编造） + RAG（KB599 + 你的简历/长期记忆）。
生成不是终点——简历是可持续「增删改查」的活文档：生成后继续对小职说「加一段开源项目 / 删掉这条 / 数字改成 200k / 给我看上一版」，小职即时在 Canvas 改；每次改动留存版本（资产·简历版本，挂该 JD），可随时回溯对比、导出。始终锚在这条 JD + 这份简历上。
与 BOSS 的根本区别：无雇主侧/投递/HR 沟通——JD 只是原料。重心是「把这一枪打准」，且这一枪由 Agent 打。

08 待确认决策点

  1. 移动端底部 4 tab 的取舍：机会/准备/小职/我的——是否认可？或想把「准备」与「小职」合并、腾位给别的？（推荐维持 4）

  3. 准备-移动端：阶段分段器 vs 左右横滑整列 Kanban，你更倾向哪种手机手势？

  5. 公司氛围数据源：目标公司库当前情报的覆盖与时效是否足以支撑"氛围"能力？不足时先只做"有据可查的部分"，无据明说。
