一句话结论 CareerMate 的一等公民应从「能力场景（简历/JD/面试/薪资 tab）」改为「一个求职机会」。用户体感是「跟小职一直聊」（A：机会内连续、检索式上下文、不切场景），系统在背后按机会自动分组并叠加投递看板与可复用资产（B：自动软分组 + 资产平铺 user 级）。目标不是复刻豆包，而是做豆包做不到的：跨机会复用八股题库、投递进度看板、把简历/面试记录当成一等资产管理。

01 背景与问题

现状（分支 careermate-rebuild-plan-v3）：前端为「机会 / 小职 / 面试准备 / 市场 / 我的」5+1 tab，进入小职时按场景类型（JD_PREP / INTERVIEW / MARKET / RESUME / GENERAL）各自开一条独立会话（agent_sessions），上下文按 ≤20 条消息 截断。

痛点
  • 对话不连续：切 tab = 换会话 = 小职失忆
  • 跨场景割裂：同一个岗位的「改简历→面试→谈薪」被拆到 3~5 条失忆会话
  • 强制选场景类型：一次准备本就横跨所有场景，却逼用户上来选一个 type —— 最反直觉的一处
  • 串台隐患：≤20 条截断，多机会并行时上下文互相污染
诊断

边界画在了错误的轴上：把「知识库/场景的边界」当成了「会话的边界」。

而求职是一条跨库的连续任务线——用户心智是「我在准备某个岗位」，不是「我在用薪资功能」。会话数量应等于用户真实在准备的机会数，而非「场景数 × 机会数」。

02 设计目标与非目标

目标（In Scope）非目标（Out of Scope）
  • 机会内对话连续、跨场景不失忆
  • 多机会并行不串台
  • 零归档负担：系统自动按机会分组
  • 资产 user 级平铺、跨机会可复用
  • 投递进度看板（替代用户手工 Excel）
  • 抗海投：浏览零建档、懒创建
  • 不重建重量级「工作空间向导」（选 type / 填表单）
  • 不做时间旅行 / from-checkpoint fork（沿用 v3.1 降级口径）
  • 不在本轮改动 RAGForge 五库结构（scene→kbId 复用现状）
  • 不改鉴权 / 组织 / 计费主链路

03 核心决策：A+B 模型

ADR-C1 · 一等公民
组织单位 = 「求职机会（Opportunity / Target）」，不是能力场景。

机会 = 一次针对具体岗位/公司的准备。JD 只是它可选的附件与冻结快照——兼容内推、海投等无干净 JD 的入口。参照成熟 CRM / 招聘 pipeline 工具，一等对象永远是「一个 opportunity」，而非「一个功能模块」。

ADR-C2 · 会话组织（B：自动软分组）
一机会一条连续会话，由系统自动成组，用户从不「手动建工作空间」。

当用户真正开始「为某机会干活」（定制简历 / 准备面试）时，系统懒创建一条轻量会话线并归到该机会名下。用户永远只是在「跟小职聊天」；回看时「我的准备」自动列出各机会。废弃「选场景 type」动作。

ADR-C3 · 上下文装配（A：检索式，不截断）
机会内上下文由「当前机会全量 + 相关历史检索」装配，废弃 ≤20 条硬截断。

串台的病根是截断而非「单线程」本身。将 MessageChatMemoryAdvisor 升级为「机会作用域 + 检索式」记忆装配：机会内连续不切场景（用户贴 JD→生成简历→分析→面试 一气呵成），跨机会天然隔离。

为什么不是「一条全局线」、也不是「像豆包一样手动新建对话」

豆包 / DeepSeek 在一条会话里连续处理单个岗位之所以不串台，靠两点：① 全量喂上下文（不做 20 条截断）；② 多岗位时用户下意识「新建对话」手动分组。即它本质也是「一岗一会话」，只是让用户手动折叠。垂类产品若只做全局线则比豆包更差，只做手动工作空间则与豆包打平——都没有存在理由。

维度 一条全局线 豆包 / DeepSeek CareerMate 目标（A+B）
机会内连续（贴JD→简历→面试）✔ 但易被截断污染✔✔
多机会不串台✘ 全糊一起△ 靠用户手动新建对话✔ 自动分组
归档负担零✘ 手动新建/命名零（系统自动）
跨机会复用八股题库✘✘ 困在某条线✔ 资产 user 级
投递进度看板✘✘ 仅倒序对话列表✔ pipeline
结构化资产（简历版本/面试记录）✘✘ 埋在聊天文本✔ 一等对象
差异化立论一个垂类求职助手不比通用助手强，就没有存在的理由。CareerMate 的护城河正是豆包做不到的三件事：把散落八股攒成可复用题库、把多机会铺成投递看板、把简历版本/面试记录当成可管理的资产而非聊天记录。

04 资产归属模型（已核实现状）

下表基于 src/main/resources/db/migration/ 源文件核实。核心原则：会话是「过程」，可归档可清；资产是「产出」，永久属于 user，与机会/会话生死无关。

数据归属键删会话性质证据
简历 + 简历版本user_id保留资产·长存V13，无 session 外键 / 无 CASCADE
职业档案user_id UNIQUE保留资产·长存V7
长期记忆（A4 pgvector）user_id保留资产·长存V32，软删，无 session 字段
职业任务user_id保留资产·长存V8，软删
面试模拟记录user_id保留资产·长存V6，独立于 agent_sessions
对话消息历史session_idCASCADE 删过程V2，ON DELETE CASCADE
工具调用 / 任务状态session_idCASCADE 删过程V2
workspace_metadata (JSONB)session_id随会话删上下文快照V17，挂 agent_sessions
好消息当前代码中不存在删除 agent_sessions 的逻辑（全量 grep 无 DELETE FROM agent_sessions、无归档）。今天没有任何资产在丢失——「资产消失」是尚未定型的假想风险，正好在本设计里定对。

三条资产红线（本设计强制约束）

红线
  1. 会话只归档不硬删：引入 status=ARCHIVED 软删，连对话历史都可回看，彻底消除「资产消失」焦虑。
  2. 凡用户会当资产的东西，一律建独立 user-owned 表，严禁塞进 workspace_metadata JSONB（该字段仅存可重建的上下文快照）。
  3. 浏览零副作用：点开 JD / 海投打招呼不建任何会话，仅「开始为此机会干活」才懒创建。

中国国情化：面试资产天生两层

通用八股题库（user 级 · 跨机会复用）Java 并发、MySQL 索引、算法题、行为面 STAR 库……不属于任何单个机会，是用户最大的一坨可复用资产。这是「资产平铺 user_id」在中国场景下最强的理由。
机会专项（机会标签）「字节爱考什么」「这家的面经」……通过 target_id / jd_id 标签归位到具体机会。

平铺 user_id + 可选机会标签 = 两者同时满足：八股全局复用、专项按机会归位。旧的「场景硬隔离工作空间」会把八股困死在某条会话里，换个公司又要重来——在中国海投场景下是明确的错误。

05 目标信息架构与页面改版

导航重构

现状： 机会·小职·面试准备·市场·我的

06 Pipeline 状态维护机制

设计立场看板的阶段是「用户与小职对话的副产品」，不是另一张需要手工维护的进度表。用户为每个机会本就在跟小职聊，系统即可从「聊什么」反推阶段——用着用着看板就维护好了。凡是「另一个要手动更新的进度表」最终都会像 Excel 一样被弃用，本机制的第一原则就是规避这一点。

三层维护机制

第一层 · 对话推断（主力 · 零动作）

从用户对小职的意图自动推进阶段，覆盖 CareerMate 真正参与的环节：

用户对小职的动作 / 意图自动推进到动作成本
让小职定制简历 / 生成投递版本准备 / 投递零
「帮我准备 X 的面试」/ 跑模拟面试 / 查这家面经面试中零
「给 35K 合理吗」/「怎么谈」/ 谈薪意图Offer / 谈薪零
某机会 N 天无任何交互仅提示，不自动改—

第二层 · 一键确认（补平台外空白 · 单击）

平台外发生的事（HR 在 BOSS 约面、笔试通过）CareerMate 观测不到 → 小职主动提示 + 用户单击确认，例如：「字节二面过了吗？」→ 点【过了】即进 Offer 列。是单击，不是填表。

第三层 · 手动兜底（少数例外）

拖卡 / 改阶段，给系统推断不到的场景留口子。永远可用，但应是例外而非常态。

边界修正（对齐懒建档红线）
  • 看板只跟踪「与小职有过交互」的机会。纯海投打招呼在 BOSS 平台内发生，CareerMate 看不到，不进看板——否则是既跟踪不到、跟踪了也是死数据。
  • 用户「收藏但还没动」的 JD 进独立暂存区（不占 pipeline，一键转为机会），与「正在准备的机会」分开，避免看板被灌水。
  • （已据此修正 mockup② 中原「海投 12 / 未建档 10」的口径。）
明确不做（近期） 深度集成 BOSS / 邮箱自动同步阶段：源头在外部平台、BOSS 抓取受风控脆弱（历史 code 36/37）、成本高且收益不稳，列为长期可选，不进 C 阶段。近期仅靠「对话推断 + 一键确认」两层覆盖绝大多数真实维护动作。

09 风险与降级

风险缓解 / 降级
检索式上下文装配复杂度上升、可能漏召回关键上文降级：机会内全量喂（机会消息量通常可控）；仅超长机会启用检索式；保留「本机会全部消息」兜底注入
自动分组误判（把 A 机会消息归到 B）提供「移动到其他机会 / 合并机会」轻量操作；新机会以显式「开始准备」为强信号，弱信号仅提示不自动切
存量会话迁移错聚迁移脚本 dry-run + 抽样核对；无法归并者保留原样落「通用对话」，不丢数据
看板阶段与真实流程不符（如校招含笔试）阶段可配置；预置社招/校招两套模板
